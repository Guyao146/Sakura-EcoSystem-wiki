# Sakura-License 采用与授权指引

> Wiki 文档版本：`v1.3.0` · 更新日期：`2026-10-04`（许可证采用指引独立版本）

本页用于把 [Sakura-License v1.2](sakura-license.md) 落实到不同项目，不是已签署的商业合同或贡献者协议。v1.2 已于 2026-10-04 发布固定正文（[正式版](../licenses/Sakura-License-1.2.md)）；项目采用仍须完成本页的权属核查并作出明确采用声明，不能仅复制一个文件就宣布整个生态改许可。

## 先完成权属核查

1. 盘点原创代码、外部 PR、复制片段、图片字体、文档引用、运行及构建依赖，记录权利人和原许可；维护者、仓库管理员身份不等于拥有全部版权。
2. 对外部贡献核实原有授权是否覆盖拟议再许可和商业例外；不足时另行取得同意、保留其原许可并合理分离，或替换实现。不能靠新贡献条款追溯取得旧贡献的权利。
3. 按具体许可版本、组合和交付方式审计兼容性。GPL/AGPL、LGPL、MIT、Apache 等不能只按“强弱”排序；LGPL 的链接路径、独立聚合、例外或双重授权需要分别分析。
4. 旧 GPL 版本的合法接收者仍可依旧许可使用、修改、再分发；新许可不能消灭这些权利。对自己拥有完整权利的内容可另行授权，但不能把他人的受限制贡献一并覆盖。

核查产物应包括文件范围清单、依赖许可清单及授权证据；有未解决冲突时，不宣称全仓库已迁移。

## 每个项目单独作采用声明

正式采用时，项目根 `LICENSE` 应放完整、固定版本正文。另以根 `NOTICE` 或 `LICENSING.md` 明确以下字段，不把 Wiki 导读或解释性页面当作许可证正文：

| 字段 | 必须明确的内容 |
| --- | --- |
| 项目身份 | 项目名、官方仓库、原始来源 |
| 权利主体 | 各相关许可人、维护者及其授权身份 |
| 适用范围 | 文件、模块、文档、资产范围及逐项排除内容 |
| 固定版本 | 正式许可版本、正文文件位置和校验值 |
| 生效边界 | 首次采用的项目版本或提交、发布日期 |
| 历史权利 | 原许可适用的历史版本；不追溯撤销旧授权 |
| 第三方内容 | 原许可、副本、NOTICE 及获取源码的要求 |
| 联系方式 | 有效的商业授权和法律通知入口 |

不要把他人项目的版权人一律写成 Guyao146。Logo、商标和域名应单独声明，不因代码许可而获得官方背书。

npm 对自定义许可的推荐写法如下；发布包根目录必须实际带有对应文件：

```json
{
  "license": "SEE LICENSE IN LICENSE"
}
```

这是元数据片段，不是项目完整 `package.json`。支持自定义 SPDX 引用的 SBOM 工具可使用 `LicenseRef-` 并附许可正文或解析映射；它不是已登记、已获 OSI 批准的 SPDX 标识，不能据此假定所有包管理工具支持。

## 商业授权单独确认

需要的是有权主体的明确书面接受，而不是申请者发出邮件或得到自动回复。建议商业授权文件至少写明：

- 许可人及其权利依据，被授权的个人、公司和允许代为操作的主体；
- 项目、模块、版本、使用方式、服务范围、地域、期限及费用；
- 是否允许交付客户、再分发或转授权，哪些对象需另行取得授权；
- 默认只放开商用限制，署名和源码义务继续适用；如要闭源等额外例外，逐项列明并确认许可人有权授予；
- 终止、续期、违约补救、停止服务后的义务及争议处理；
- 第三方组件、历史授权和法定权利不被该合同擅自变更。

不公开客户合同、身份资料、密钥；可在公开 Issue 中询问联系渠道，再通过私密渠道交换材料。沉默或未在一定天数内答复不等于授权；本指引不承诺审批期限。

## 贡献者授权单独取得同意

普通贡献可以按项目明确的入站许可接收，贡献者保留其版权。你对独立拥有完整版权的内容无需给自己申请商用许可，但如果贡献仅按非商用条款授予，项目对包含该贡献的版本收费运营，可能同样缺少必要权限，并非只有闭源或换许可证时才需要核实。

### 推荐在首次接收贡献前落实的授权

项目拟继续统一商业运营时，应先用独立协议明确取得以下范围的授权，并保存真实同意记录；以下是协议拟定要求，不是已经生效的 CLA：

- 明确受授权的个人或法人、项目、贡献者及其有权代表的主体、涵盖的 PR/提交或经同意的后续贡献范围；不能只写“所有维护者”。
- 明确授予非独占的复制、修改、分发、公开展示及网络服务等必要权利，覆盖项目的商业运营，并允许向客户授予约定范围内的商业使用许可；明确地域、期限、对价及终止条件，不留作“提交后再解释”。
- 推荐默认商业再许可仍保留署名和对应源码义务；如还需要闭源或不同许可证发布，须事先另行明确告知并取得同意，而不是从“商业使用”推定全部例外。
- 贡献者保留版权与依法自行使用其原创贡献的权利；贡献者是否有雇主授权、是否包含第三方材料及不可再许可部分，均需列明。
- 专利、代表维权、历史侵权追诉等额外权限单独核实，不从普通非独占许可中推定。协议应明显提示重要条件，记录固定文本版本及同意方式。

未经相应权利人的同意，不把贡献标记为可商业再许可；可以继续按已有有效授权的范围使用、补充取得授权，或在有权范围内分离替换。向原项目提交补丁的源码托管例外，也不等于授予项目这些入站权利。

| 事项 | 接收前的核查 |
| --- | --- |
| 贡献身份 | 贡献者及其有权代表的主体、职务成果或雇主权利 |
| 贡献范围 | 对应 PR、提交或明确列明的后续贡献范围 |
| 授权内容 | 复制、修改、分发，以及是否明确允许商业再许可 |
| 保留权利 | 不把非独占授权误写成版权转让 |
| 第三方材料 | 来源、原许可、无法额外授权的部分 |
| 专利与维权 | 需要的额外权利单独约定，不假定自动取得 |
| 同意证据 | 协议固定版本、确认人、时间和确认方式 |

仅在后来的 LICENSE 中补一句“提交即同意一切再许可”，不足以证明旧贡献者已同意。DCO 或 Signed-off-by 也不应被当作未明示的商业再许可授权。

## 受托处理与运营安排

依正文第 6 条第 8 款使用受托处理例外前，应留存委托方、受托方、用途、涉及副本及版本、访问权限、保密约定、必要转委托审批、结束后的归还或删除安排。必要的受托开发、修改及成果返还同样应纳入范围；受托方不得把副本独立使用或向其他客户提供受覆盖功能，仍须保留原声明、来源和变更记录。交付文件不等于取得文件中所有新增成果的版权，开发协议应另行明确成果许可与归属。

受托处理与商用授权分别判断：客户内部版本不因满足条件的审计、私有构建或运维交付就必须向公众公开，不等于专项收费部署、定制或维护服务自动获得商用授权。仅收费提供通用计算、存储、网络或私有构建基础设施，不因客户在其上运行本作品而单独触发商用授权。若受托方成为对外托管服务的运营者，应按通常分发、服务和商用规则核查。

纯协议应用收取自己的服务费，不会取消互操作例外；API 服务提供者若希望限制转售、配额或访问，应通过有效的服务合同明确，而不是用与协议例外冲突的版权条款暗中限制。复制 SDK 应核对 SDK 自身许可，不能把服务访问合同当作实现代码的授权。

## 原项目评审与付费任务

对于通过原项目认可渠道提交的 PR、补丁或私密漏洞修复，记录基础版本、修改范围、来源和提交者许可，保留足够评审及重建改动的材料。正文第 6 条第 10 款不要求贡献者另建下载站或持续托管三年；合并、公开发布和商业运营前，维护者仍须确认各自所需权限。将客户交付或另行发行伪装成评审不适用该例外。

悬赏、采购订单或开发协议可以按正文第 4 条第 5 款直接包含任务许可，须写清：

1. 谁对所涉原代码有权授权、谁可以承接任务；公开任务还应说明承接者的确定及授权成立方式。
2. 允许的项目版本、修改测试范围、交付对象、期限和任务报酬；现有商业许可是否已覆盖，不要求对同一已授权行为重复申请。
3. 非公开评审或受托返还适用哪一例外；如有其他例外，逐项明确，不能以任务报酬推定。
4. 新成果的入站许可、成果归属、第三方材料和验收记录；任务完成不自动赋予承接者向其他客户销售或托管的权利。

没有明确任务许可时，只有“付奖金”、维护者发 Issue 或收到补丁，不能替代充分授权；受托开发的非公开例外也不能代替承接者需要的专项商业服务授权。

## 授权核验与通知记录

正式发布前，除权属清单外还应准备可执行的采用声明、商业授权文件、需要的贡献者协议及同意流程。这些文件须经过确认并实际使用，本指引本身不是已签署的授权：

- 核实签发者与各受覆盖部分的权利依据，不能仅凭仓库管理员头衔判断其有权作商业例外；
- 记录授权标识、对应许可文本或校验值、签发与接受时间、主体、版本、用途、到期日、允许代为操作者及转授权范围；
- 指定有效的申请、核验和法律通知渠道，记录通知对象、版本、具体事项与到达证据；不把公开 Issue 留言视为已送达的保证；
- 公开授权核验信息应最小化，私人保存合同、身份和证明材料，不要求客户在公开仓库暴露商业资料。

主动纠正应记录发现时间、受影响版本、停止新交付或服务的措施、补齐后的源码和署名地址及完成时间。首次非故意遗漏可按正文第 12 条核查恢复条件；不属于该情形的、曾纠正后再次违约或逾期未纠正的，不能自行把授权标记为已恢复。恢复不抹去既往责任，重新下载不重置终止状态。

## 源码保留与安全披露

先按正文第 6 条确定交付方式。仅转发未修改的完整源码或已包含可编辑源文件的完整文档、资产，随副本完整保留许可与来源并实际交付材料，可按第 11 款履行，不另建公共下载站或新增三年托管义务。抽取改编、仅有渲染产物、附带二进制发行或运营服务不能自动套用这一方式；收费仍按商用规则判断。

对于适用同步公开规则的修改版、二进制交付和服务，对每个实际对外版本记录首次交付或上线时间、最后分发和停止服务时间、对应源码地址及至少 3 年保留期限。转发未修改的二进制或非源码文档产物仍按第 12 款核实上游固定源码地址并准备备份镜像；发现失效及时补充，恢复前停止新增转发，不能以停发解除旧交付的保留义务。仅分享官方链接不新增托管义务。

未对外提供的内部测试分支不在强制公开范围，也不要求公开完整 Git 历史；不得因此缺少实际交付版本及必要变更说明。原项目评审和限定受托处理适用各自例外，不应让提交补丁或返还内部修复的人承担无关发布责任。

对于仍适用同步公开的交付，互联网免费获取是 v1.2 正文自主选择的严格条件，并非所有许可证或法律的通用要求；例如向一个客户私下交付修改版二进制，在没有适用例外或有效独立授权时仍会触发。正式采用应确认该规则与客户保密安排能同时履行。

安全修复不自动享有延期。内部测试阶段可先协调升级；将修复版本用于对外服务前，若确需限制源码披露，应取得有权主体就版本、材料、理由、期限及到期公开方式作出的有效书面安排，并检查其他许可义务是否允许。没有书面安排时不能自行推迟公开，也不能靠标注“安全相关”无限延期。

## 发布前核查

1. 对照已批准正文核对根 LICENSE、采用声明、README、网站、包清单及第三方通知，避免同一范围出现互相矛盾的授权。
2. 实际打包并解压检查许可副本、署名和版本标识；运行 GUI、CLI、API 后确认用户能找到对应源码。
3. 验证公开地址可不经付款、注册或审批下载对应源码，并按说明重建；配置示例不含密钥和用户数据。
4. 保存固定版本文本、权属确认和商业/贡献授权记录，按源码保留期维护已交付版本。本指引不等于已完成这些检查。

正式发布已按此执行：审阅期的状态提示、修订过程和“尚未生效”说明保留在 [审阅稿存档](../licenses/Sakura-License-1.2-draft.md) 与导读版本记录中；正式 LICENSE 使用固定正文 [Sakura-License-1.2](../licenses/Sakura-License-1.2.md)，项目采用声明记录范围和起点，FAQ 只解释而不增加义务，商业及贡献者协议各自承载额外授权。已针对正式稿重新检查交叉引用；后续版本变更同样不能只删掉标题里的版本标识就视为迁移完成。
