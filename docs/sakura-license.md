## 修订后的核心规则

1. **商用按交易判断**：对外提供受覆盖作品或服务并收取对价需授权，组织纯内部自用不因公司身份自动算商用。付费支持、绑定功能的赞助、直接广告对价及收费套餐不能以“软件免费”规避。
2. **互操作有明确例外**：独立客户端仅通过公开 API/MCP 调用不承担本许可的署名、商用授权或源码义务；不因客户端收费或转售调用结果而丧失例外。复制实现或自行提供受覆盖功能另行判断，服务商本身的转售、访问、额度及收费合同仍有效。
3. **源码义务按交付方式区分**：通常的修改版发布、二进制分发和对外服务须同步免费公开对应源码，停止该对外版本分发和服务后至少保留 3 年；不能靠关停、换域名或重上线清零。内部使用、限定受托处理、原项目评审提交有明确例外；仅转发未修改的完整源码或可编辑文档，不另要求公共托管。未对外提供的内部测试版和完整 Git 历史不在强制公开范围。
4. **范围不过度扩大**：受覆盖的改编作品按同一固定版本共享，独立聚合及第三方组件不因此改许可；单纯复制模块、包装改名也不能掩盖实际改编。
5. **源码可编辑、可重建**：包含必要构建材料和脱敏配置，不接受只有混淆代码或失效链接；不要求公开密钥、用户内容、个人信息和无关业务数据。
6. **商业许可不是默认闭源许可**：默认只放开商用条件，其他义务继续适用；额外例外须由有权主体逐项书面批准。新许可不自动获得贡献者版权、全部模型权重或历史再许可权。

以上均为拟议规则，不应当作 v1.0/v1.1 已经包含的义务。同步公开、3 年保留等实质变化需审查后另行明确采用。

## 典型使用场景

下表解释审阅稿，不是对现有历史版本的重新解释。“署名”不要求每屏重复，但应保留原声明并在适当入口可找到；法定例外及有效的独立授权优先按其适用范围处理。

| 场景 | 另行商用授权 | 署名 | 对应源码 |
| --- | --- | --- | --- |
| 同一公司内部修改自用，未对外提供 | 不需要 | 保留原声明 | 不要求公开 |
| 商业 Agent 仅调用他人的公开 MCP/API | 不因调用或独立客户端收费需要 | 不因调用需要 | 不要求公开客户端 |
| 内部系统交由符合第 6 条第 8 款的受托方处理 | 委托方不因该交付需要；专项收费服务另判 | 保留原声明和修改记录 | 不会仅因受托处理要求公开 |
| 私有 CI、通用云存储或计算基础设施 | 通用基础设施费用本身不触发 | 保留副本声明 | 满足受托条件时不要求公开 |
| 不交付或操作受覆盖作品的独立评论、课程或咨询 | 不因收费或提及项目需要 | 法定引用按法律要求 | 不触发本许可源码义务 |
| 免费对外运行原版或修改版服务 | 不需要 | 需要 | 启用时同步公开对应版本 |
| 仅向原项目指定渠道提交补丁或安全修复供评审 | 无偿提交不需要；收费任务按明确授权 | 保留来源、许可及改动说明 | 不另建下载站；提交足够评审材料 |
| 仅转发未修改的完整源码或可编辑文档 | 按交易判断 | 随副本完整保留 | 实际交付材料即可，不新增三年托管 |
| 转发未修改二进制或不含源文件的文档产物 | 按交易判断 | 需要 | 上游固定源码地址或镜像，通常仍保留三年 |
| 受托修改内部版本并返还成果 | 专项收费任务须明确授权 | 保留原声明和修改记录 | 符合受托条件时不因开发和返还而公开 |
| 自愿无实质回报捐赠，免费分享修改版 | 不需要 | 需要 | 分发时同步公开 |
| “赞助”绑定账号、额度或优先支持 | 需要 | 需要 | 默认仍须同步公开 |
| 收费 SaaS、交付、部署或维护 | 需要 | 需要 | 默认仍须同步公开 |
| 镜像中聚合独立数据库和受覆盖应用 | 按交易判断 | 受覆盖部分及第三方通知 | 不据此要求独立数据库改许可 |
| 公开复制受保护文档片段，非法定例外 | 按交易判断 | 需要 | 公开受覆盖内容及其改编的可编辑形式 |
| 仅放链接或依法适当引用 | 不因本许可需要 | 按适用法律 | 不触发本许可源码义务 |
| 出售不含受覆盖内容的独立生成视频 | 不因使用工具本身需要 | 不因使用自动需要 | 不要求公开用户内容 |
| 对外发布含受覆盖语料的数据集 | 按交易判断 | 需要 | 公开受覆盖部分，不当然包括全部模型权重 |

纯协议调用不是“先复制实现再套 API”的免责路径；反过来，也不能因为服务端使用了本作品，就要求所有独立调用方开源。对外收费提供工具功能与出售独立输出是不同场景。

## 模块、SDK 与插件案例

以下是第 1、2、5 至 7 条的说明，不根据文件扩展名、打包工具或进程数量自动判定整套系统必须共享；涉及具体组合的法律结论仍需结合实际代码与结构审查。

| 使用方式 | 应核查的范围 |
| --- | --- |
| 复制受保护函数并修改 | 受覆盖函数及其改编须保留许可；若形成一体化改编作品，共享及于受覆盖整体，而非自动扩展到无关仓库 |
| 直接导入 npm 模块 | 模块自身适用许可不能忽略；调用程序是否形成受覆盖整体取决于实际复制、改编与组合，不以“只是依赖”当然豁免 |
| 插件或动态链接库 | “插件”“动态链接”名称既不自动豁免，也不自动要求所有宿主代码共享；需核对实现、接口、组合及第三方许可 |
| 独立进程通过公开协议通信 | 不因通信本身触发调用方义务；拆成进程不能洗掉已复制的实现 |
| 使用官方 SDK | 纯 API 例外不等于 SDK 例外；SDK 须有明确的自身许可，项目可在有权范围内另行给 SDK 授权 |

## 贡献、转发与付费任务

正文第 6 条第 10 款允许通过原项目认可的 PR 或安全渠道提交补丁供评审，不要求贡献者另建公开下载站、保持三年托管或提交无关私人源码；许可、来源、基础版本和足够评审材料仍需保留。这不是向客户发行修改版的例外，公开合并后的发布者按实际交付承担义务，也不因提交就自动获得贡献者商业授权。

第 6 条第 11 款减轻普通转发者负担：未修改的完整源码或已带齐可编辑源文件的文档可以随副本交付，不另建托管站。转发二进制、PDF 等非源码产物按第 12 款处理；可以核实后引用上游固定源码地址，但要有失效后的镜像安排，恢复前停止新增转发。仅分享官方链接不产生这一托管义务。

你对自己独立拥有完整版权的部分不必给自己发商用许可。但接收外部 PR 后，即使保持源码公开，收费运营含这些贡献的版本也要确认商业使用权；建议在首次接收贡献前，按 [采用指引](sakura-license-adoption.md) 明确指定受授权主体并取得可核实的非独占商业使用及必要商业再许可授权，不能将建议当作贡献者已同意的协议。

有权主体的悬赏或开发协议可以明确包含完成指定任务所必需的许可，避免承接者再为同一任务重复申请。只有已经书面覆盖的范围才获授权；报酬不自动授予向其他客户经营的权利，成果返还不自动转让新增版权，入站授权仍需确认。

## 受托处理、补救与安全披露

内部版本交给云服务、私有 CI、安全审计或开发运维人员，只有符合正文第 6 条第 8 款的限定用途、保密、权限及归还删除条件，才不因该处理、必要开发修改或成果返还新增公众源码义务。不是所有“外包”都豁免：受托方收费进行专项开发、部署或维护的商用授权另行判断；成果权属单独约定，已经对外提供的版本不能靠改称“受托”取消公开义务。实际采用前应按 [采用指引](sakura-license-adoption.md) 保存安排和证据。

首次非故意遗漏署名或源码要求，尚未收到该许可人的通知且无此前纠正恢复记录，主动停止受影响的新交付或服务并完整纠正后，可按正文第 12 条第 3 款恢复。未授权商用不走该自动路径；首次通知后的补救、重复违约等按同条其他款处理，不能换账号或重新下载重置。

安全修复没有自动延期：内部测试、符合条件的非公开评审或受托处理按各自例外判断；用于适用公开规则的对外服务或交付时，仍须同步公开对应源码。确需协调披露，应事先取得有权主体对具体版本、材料和期限的书面安排；“涉及安全”不是自行无限延迟的理由。

## 名称与法律边界

限制商用不符合 [OSI 开源定义](https://opensource.org/osd) 对商业用途的要求，应称为“源码可用”或“共享源码”，而不是宣称已获 OSI 批准。GPL/AGPL 允许商业使用，并不是附带禁商用条件的等价替代。

本页及审阅稿不保证没有漏洞或在所有司法辖区均可执行。重要条件应明确提示，正式采用前应由熟悉软件版权与许可的律师结合项目权属、贡献和商业安排审查。文档检查只能验证结构、链接和部分文本一致性，不能证明法律有效性。
